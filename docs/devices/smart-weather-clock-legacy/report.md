## Compatibility with this integration

Checked against `custom_components/geekmagic/device.py`, `profiles.py`, and `const.py`. Every method on `GeekMagicDevice` delegates to a `FirmwareProfile` adapter. The three original concrete adapters (`StockUltraProfile`, `StockProProfile`, `SdProProfile`) — plus the `UnknownStockProfile` fallback — all point at endpoints this device doesn't have, which is why `WeatherClockLegacyProfile` exists as a fourth adapter.

### What likely breaks on the original three profiles

- **`detect_model()` / `detect_firmware_profile()`** — tries `/v.json`, `/.sys/app.json`, `/app.json`, `/theme/list` in order and falls back to `UnknownStockProfile` (`MODEL_UNKNOWN`) if all fail. All four return HTTP 404 on this device (confirmed with a direct probe).
- **`test_connection()`** calls `get_space()` → `GET /space.json`, which 404s. Config flow setup is correctly rejected instead of silently creating entities that never update.
- **`get_state()`** → `GET /app.json` — 404. This device exposes state field-by-field as plain text via `GET /home?num=<n>` / `GET /Checkbox?num=<n>`, discoverable only by reading `javascript.js`'s `window.addEventListener("load", …)` block.
- **`get_brightness()`** → `GET /brt.json` — 404. Read the same field-by-field way; set via `GET /updateLEDBrightness?ledBrightness=<2-99>`.
- **`set_theme(theme)`** → `GET /set?theme=<n>` — this device instead uses `GET /save?option=<1-5>` for a decorative GIF picker, and a *separate* `themeselect` dropdown (Classic/Simple/Photo/Dial) for the actual top-level display mode. Neither matches `/set?theme=`.
- **`upload()` / `display_rendered_dashboard()`** → `POST /doUpload?dir=/image/` with multipart field `file` — this device exposes `POST /upload` with multipart field `imageFile` instead. Wrong path *and* wrong field name.
- **`delete_file()` / `clear_images()` / `get_image_files()`** → `/delete?file=`, `/set?clear=image`, `/filelist?dir=/image/` — none of these exist. Instead there are five fixed photo slots (`/file1`–`/file5`, static JPEGs) with individual enable checkboxes.
- **`navigate_next()` / `navigate_previous()` / `navigate_enter()` / `reboot()`** — no menu/page-navigation concept at all. Restart is a plain `GET /restart`, wired to a "System Restart" button.

## How `WeatherClockLegacyProfile` actually works (confirmed on real hardware)

The single biggest surprise building this profile: **`themeselect` (Classic=0/Simple=1/Photo=2/Dial=3) is a separate top-level mode selector from `giflist`** (the decorative GIF picker), and it gates whether *anything* photo/GIF-related is visible at all. An early version of this profile only touched `giflist`; with `themeselect` left on Classic, nothing was ever visible on the physical display, despite every HTTP call succeeding. Confirmed by watching the real device: switching `themeselect` to `2` (Photo) made it start cycling its 5 photo slots immediately.

Given that, the profile:
- Reads state via `/home?num=1` (theme/themeselect) and `/home?num=8` (brightness).
- Sets brightness via `GET /updateLEDBrightness?ledBrightness=<2-99>`.
- Sets theme via `GET /themeselect?getstate=<n>` — confirmed working and persists via `/home?num=1` readback.
- Uploads always target photo slot 1: `POST /upload` (field `imageFile`) saved as `file1.jpg` — confirmed by re-fetching `GET /file1` and byte-comparing against the uploaded content.
- Displaying an image enables slot 1 (`GET /file1-switch?getstate=1`), disables slots 2–5 (`GET /file<N>-switch?getstate=0`), and switches `themeselect` to Photo (`2`) — confirmed live: this pins a single static image instead of cycling through 5 slots.
- Once already in Photo mode, `set_image()` skips the slot-isolation calls on subsequent pushes (only the upload itself is needed) — the coordinator calls this on every refresh cycle, so redoing all 6 HTTP round-trips every time added real, avoidable latency on real hardware.
- Reboot is `GET /restart` — not directly exercised against hardware, taken from `restartESP()` in `javascript.js`.

### A second real hardware bug found and fixed along the way

Pushing a rendered dashboard raised `aiohttp.ClientResponseError(400, "Data after \`Connection: close\`: ...")` on `POST /upload`, aborting the push before it ever reached the theme-select step — despite the device's own response body containing `Upload successful!`, proving the write itself completed and only the HTTP response framing was malformed. `get_text()`/`get_bytes()` already tolerate this exact error class via `is_malformed_firmware_response()` + a raw HTTP/1.0 fallback; `post_file()` had no equivalent handling. Since the write already succeeded, there's nothing to retry — `transport.py` now just swallows the framing error the same way the GET path does.

## Endpoints by feature

### Identification & system

- No identification endpoint. `/v.json`, `/.sys/app.json`, `/app.json`, `/theme/list`, `/space.json`, `/brt.json`, `/album.json`, `/config` all confirmed `404 Not found: <path>`.
- `GET /restart` *(state-changing)* — reboots the device (`restartESP()` in `javascript.js`).
- `GET /update` — confirmed to be a stock [ElegantOTA](https://github.com/ayushsharma82/ElegantOTA) page, served as raw gzip **without** a `Content-Encoding: gzip` header (a common `ESPAsyncWebServer::serveStatic()` gotcha). Nothing custom lives there.

### Display

- `GET /save?option=<1-5>` *(state-changing)* — decorative GIF picker: `1`=spaceman, `2`=bird, `3`=totoro, `4`=hutao, `5`=customization. Not used by this profile.
- `GET /themeselect?getstate=<0-3>` *(dynamic, confirmed working)* — top-level mode: `0`=Classic, `1`=Simple, `2`=Photo, `3`=Dial. This profile only ever sets `2`.
- `GET /updateLEDBrightness?ledBrightness=<2-99>` — brightness, confirmed via readback.
- `POST /led` (form field `ledBrightness`, same range) — a second brightness path wired to the same slider; unclear which is actually live, both present in the markup.
- `GET /file<N>-switch?getstate=<0|1>` for N in 1–5 *(dynamic, confirmed working)* — enable/disable each photo slot.
- `GET /Nightmode?getstate=<0|1>`, `starttime`/`stoptime` selects, `GET /NightBrightness?getstate=<2-99>` — night mode window, not modeled by this integration.
- `GET /sendColor0`/`1`/`2?r=&g=&b=&n=<0|1|2>` — RGB clock color pickers; all three 400'd when probed with no params.
- `GET /led-state`, `/hourtime-state`, `/Mile-state` — dual-purpose: bare GET reads JSON `{"state": bool}`, `?getstate=<0|1>` sets it.
- `GET /timeformat?option=<1-3>` — `1`=MM/DD/YYYY, `2`=DD/MM/YYYY, `3`=YYYY/MM/DD.
- `GET /delaytime?getstate=<3-60>` — photo slideshow play speed in seconds.

### Network / WiFi

- `GET /scanwifi` — returns `[{"ssidList": "<option>...</option>..."}]`, an HTML fragment, not structured JSON.
- `GET /connect?new_ssid=<ssid>&password=<password>` *(state-changing)* — submits WiFi credentials as a **cleartext GET query string**. Nothing for this integration to act on, flagged for anyone else documenting this firmware.

### Content & data

- `GET /file1`–`/file5` — static JPEGs, one per photo slot. `WeatherClockLegacyProfile` uses slot 1 as its single managed file.
- `GET /file<N>-switch?getstate=<0|1>` — per-slot enable, string-concatenated in the device's own JS (`filecheck.id`), not resolvable by an automated crawler.
- `GET /Checkbox?num=<n>` / `GET /home?num=<n>` — plain-text field readback for the whole settings form (15+ fields keyed by hard-coded `num`).
- `GET /updateCity?city=<name>` — sets the weather location string.

- `GET /restart` (reboot) has not been exercised against real hardware.
- The persistent small IP-address overlay visible on the physical display in every mode appears to be a hardcoded firmware OSD with **no web-exposed control**: not in this device's own HTML/JS, not toggleable via any endpoint found (15 additional common diagnostic paths — `/info`, `/status`, `/debug`, `/sysinfo`, `/settings`, `/config.json`, `/wifi.json`, `/admin`, `/console`, `/diag`, `/version`, `/whoami`, `/ip`, `/about`, `/system` — all 404). Likely baked into the firmware's own display-draw loop.
